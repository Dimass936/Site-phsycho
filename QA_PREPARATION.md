## 🔧 Технические вопросы

### Q1: Почему выбрал именно эти технологии?

**Ответ:** Я выбирал инструменты по трём критериям: бесплатность, простота и достаточность. Для сайта взял чистый HTML/CSS/JS — фреймворк не нужен, потому что это статический сайт-визитка без сложной логики. Для бота — Python, потому что у него богатая экосистема асинхронных библиотек. DeepSeek выбрал вместо OpenAI — он понимает русский язык на том же уровне, но дешевле в 10 раз. Pollinations — единственный бесплатный сервис генерации картинок без ограничений.

**Пример:** Сравнение стоимости: OpenAI gpt-4o — $2.50/1M токенов, DeepSeek — $0.14/1M токенов. Разница в 18 раз.

**Знания:** Анализ TCO (Total Cost of Ownership), сравнение API-провайдеров, выбор инструментов под задачу, а не «потому что модно».

### Q2: Как работает Approval Flow — от /test до публикации?

**Ответ:** Это трёхэтапный конвейер. Сначала бот вызывает DeepSeek API и генерирует текст поста, параллельно — три картинки через Pollinations. Затем сохраняет всё в `bot_data` (in-memory кеш) и показывает inline-клавиатуру. Когда пользователь нажимает кнопку — срабатывает CallbackQueryHandler, который достаёт пост из кеша и отправляет в канал через Telegram Bot API.

**Пример из кода:**
```python
# generation
cache[chat_id] = {"post": post, "images": image_urls}

# approval
if data == "approve":
    url = f"https://api.telegram.org/bot{TOKEN}/sendPhoto"
    payload = {"chat_id": CHANNEL_ID, "photo": img_url, "caption": post[:1024]}
    r = requests.post(url, json=payload, timeout=15)
    if r.status_code == 200:
        mark_posted()
```

**Знания:** In-memory state management, CallbackQuery API, Telegram Bot API (sendPhoto), rate limiting.

### Q3: Какие проблемы возникли при разработке и как ты их решил?

**Ответ:** Три основные проблемы. Первая — Pollinations.ai часто не успевал отдать картинку за разумное время. Решил через `read_timeout=45` и try/except — если картинка не загрузилась, бот отправляет прямую ссылку. Вторая — бот падал после закрытия SSH-сессии. Решение: `nohup` + Google Cloud как демон, плюс `start_new_session=True` в subprocess. Третья — иерархия заголовков HTML была нарушена. Исправил через SEO-аудит: H4 → H3 на трёх страницах.

**Пример:**
```python
# Fallback для картинок
try:
    await update.message.reply_photo(photo=img["url"], read_timeout=45)
except Exception:
    await update.message.reply_text(f"🖼️ Вариант {i+1}: {img['url']}")
```

**Знания:** Graceful degradation, defensive programming, системное администрирование (nohup, демоны).

### Q4: Почему файлы, а не база данных?

**Ответ:** Для MVP база данных — overengineering. У меня четыре коллекции данных: посты на утверждении, темы, примеры стиля, даты публикаций. Это 4 JSON-файла по 5–20 КБ. SQLite добавил бы 200 строк кода и зависимость, а я получил бы те же возможности. Когда проект вырастет до десятков пользователей — да, миграция на PostgreSQL. Но сейчас файлы читаются за 0.1 мс, и этого достаточно.

**Пример:**
```python
# Approval queue — простой JSON
with open(PENDING_FILE) as f:
    pending = json.load(f)
post = pending.pop(0)
with open(PENDING_FILE, "w") as f:
    json.dump(pending, f)
```

**Знания:** YAGNI-принцип, анализ требований к хранилищу, понимание границ масштабирования.

### Q5: Как защитил бота от неавторизованного доступа?

**Ответ:** В `.env` хранится список разрешённых Telegram ID через запятую. Каждый handler вызывает `check_access()`, который сверяет `update.effective_user.id` со списком. Если пользователь не в списке — `Access denied`. Плюс rate-limiter: публикация в канал не чаще раза в неделю через `last_post.txt`.

**Пример:**
```python
ADMIN_IDS = [int(x.strip()) for x in os.getenv("TELEGRAM_USER_ID", "0").split(",")]

def check_access(update) -> bool:
    return update.effective_user.id in ADMIN_IDS

# Rate limiter
def can_post():
    if os.path.exists(RATE_FILE):
        with open(RATE_FILE) as f:
            last = datetime.strptime(f.read(), "%Y-%m-%d")
        if datetime.now() < last + timedelta(days=7):
            return False
    return True
```

**Знания:** Аутентификация, авторизация, rate limiting, безопасность переменных окружения.

## 🏗️ Архитектурные вопросы

---

### Q6: Почему именно такая архитектура?

**Ответ:** Я использовал паттерн «агентной архитектуры» — каждый агент это независимый Python-скрипт, которые общаются через файлы. Плюсы: агентов можно запускать по отдельности, заменять, тестировать изолированно. Оркестратор запускает их цепочкой. Это микросервисная архитектура без Docker — для MVP идеально.

**Сравнение с альтернативами:**
- Монолит → сложно тестировать, всё связано
- Микросервисы на FastAPI → оверхед для MVP
- Jupyter ноутбуки → не продакшен

**Знания:** Архитектурные паттерны (агентная, микросервисная), trade-off анализ.

### Q7: Как масштабируется приложение?

**Ответ:** Горизонтально: каждому пользователю — свой `.env` и экземпляр бота на отдельном порту. Или вертикально: один инстанс с очередью задач и балансировкой. Сейчас один e2-micro тянет одного бота. При росте — Docker Compose с N экземплярами.

**Текущие ограничения и решения:**
- In-memory кеш (`bot_data`) → заменить на Redis
- JSON-файлы → PostgreSQL
- Один сервер → Docker Swarm / Kubernetes

**Знания:** Масштабирование, контейнеризация, понимание узких мест.

### Q8: Какие альтернативы рассматривал для бота?

**Ответ:** Три варианта. Первый — делать веб-интерфейс на React + FastAPI. Отказался, потому что психологу удобнее чат в телефоне. Второй — использовать готового бот-билдера типа Manybot. Отказался из-за отсутствия гибкости и AI-интеграций. Третий — Discord бот. Отказался, потому что целевая аудитория (родители, пары) сидит в Telegram.

**Знания:** Анализ целевой аудитории, UX-исследование, сравнение платформ.

## 📋 Процесс разработки

---

### Q9: Как использовал AI-агентов в процессе разработки?

**Ответ:** На трёх уровнях. Первый — агенты для продукта: CMO, Content Writer, Telegram Agent. Они генерируют контент. Второй — агент-помощник в разработке: SEO Specialist проверил 7 HTML-файлов, QA Agent сделал аудит. Третий — я сам как «тимлид» управлял агентами через spawn_agent в IDE.

**Метрики:** 3 параллельных агента отработали за 5 минут и покрыли SEO + QA + Media за один проход.

**Знания:** Оркестрация AI-агентов, параллельное выполнение, делегирование.

---

### Q10: Как организовал работу?

**Ответ:** По методологии «AI-Driven Development»: сначала спецификация и архитектура → потом код через итерации → затем SEO, QA, Media агентами → деплой. Git-коммиты атомарные: один коммит — одно изменение. 30+ коммитов за проект.

**Инструменты:** GitHub для версионирования, GitHub Actions для CI/CD, Gitmoji-стиль коммитов.

**Знания:** Git-flow, CI/CD, документация проекта (SPEC, ARCHITECTURE, PLAN).

---

### Q11: Сколько времени заняло?

**Ответ:** Ядро проекта (сайт + бот) — одна интенсивная сессия. SEO, QA, медиа — запустил 3 агентов параллельно, через 5 минут было готово. Доработки (approval flow, стиль, картинки) — ещё несколько сессий. Итого: основной функционал за 1 день, полировка — ещё 2–3 сессии.

**Знания:** Оценка трудозатрат, Agile, параллелизация через AI-агентов.

### Q13: Что бы сделал иначе?

**Ответ:** Три вещи. Первое — с самого начала хранил бы состояние бота в SQLite, а не in-memory. Сейчас при перезапуске кеш теряется. Второе — использовал бы `apscheduler` сразу, а не переписывал с cron на JobQueue. Третье — делал бы approval flow с самой первой версии, а не добавлял потом. Итерация — это нормально, но MVP сразу должен включать «человек принимает решение».

**Знания:** Рефлексия, работа над ошибками, приоритизация фич для MVP.

### Q14: Чему ещё хочешь научиться?

**Ответ:** Хочу углубиться в три области. Первая — RAG (Retrieval-Augmented Generation): агенты должны читать не только Obsidian, но и векторную базу знаний. Вторая — мульти-агентные системы с LangChain/LangGraph: более сложные цепочки взаимодействия. Третья — продакшен-мониторинг: Prometheus, Grafana, Sentry. Чтобы видеть, что происходит с ботом 24/7 без захода на сервер.

**Знания:** Технологический кругозор, самообучение, карьерный рост.
